# GR Store backend: Firebase identity + Supabase PostgreSQL

The owner explicitly reaffirmed Supabase/PostgreSQL on 2 November 2026. Firebase configuration was supplied for Google/email identity only. This document supersedes the earlier Firebase-backend amendment. No further Firebase database, storage, functions, billing or IAM operations are authorized by this phase.

Keep the approved GR Store design and existing Firebase sign-in. Firebase issues user tokens. A Supabase `commerce` Edge Function verifies RS256 signatures against Google's official securetoken JWKS, exact issuer `https://securetoken.google.com/grnutritions`, audience `grnutritions`, expiration and a nonempty subject. Caller-supplied user IDs and admin claims never determine data ownership or staff rights.

Public catalog reads use the Supabase anonymous Data API and RLS to expose active products only. Private customer/address/order requests and all admin operations use the Edge Function, which passes the verified Firebase UID into service-only SQL RPCs. This pattern needs no Firebase Cloud Functions or role custom-claim bootstrap. Private tables deny direct client-role access, staff membership lives in a non-exposed schema, and service RPCs check explicit ownership or staff membership. The service key exists only in Supabase's Edge environment.

PostgreSQL holds product metadata, brands, categories, normalized variants, unique SKUs/slugs, addresses, orders and audit events. JSON product payloads preserve the existing screen contract; catalog reads rehydrate prices and stock from normalized variant rows. Product saves, address defaults and quote calculation run transactionally. Admin edits use an `updatedAt` version to reject overwriting a newer product/inventory edit. Quotes calculate integer paise from live inventory and expire; they never pretend payment or stock reservation occurred. Razorpay reservation/payment/webhook work stays in its own milestone.

Supabase Storage uses a private `product-media` bucket. The Edge Function grants staff signed upload URLs, checks content metadata before saving references, and returns short-lived read URLs for previews. Public active catalog image metadata maps only to published product image paths. A media endpoint signs paths only after verifying they belong to an active product or the caller is staff. Temporary and draft objects are never publicly listable.

The app uses `store-api.ts` as the sole private operation adapter, a Supabase catalog repository, customer address/order services and an admin service. Firebase modules export the app/auth only. Existing Firestore cloud resources are left unused; they are not deleted or migrated because no customer data was recorded by the agent. Superseded local Firebase-backend code/configuration is removed after replacement tests pass.

Verification: real PostgreSQL via PGlite tests RLS/grants, role spoofing, UID ownership, rejected cross-customer address operations, SKU/URL uniqueness, quote totals, stale versions, atomic default changes, order lifecycle and media restrictions. Edge token verification tests use generated RSA keys to prove project/audience/expiry/algorithm validation without contacting customer accounts. UI tests mock the adapter boundary; web/native exports and browser shopping/checkout/coach checks remain required. Live Supabase project creation/deployment waits for a confirmed connector or CLI account; no fictional endpoint is used.
